# Benchmark-only Redis TCP-preflight bypass experiment

Date: 2026-08-23  
Run: `preflight-bypass-low-20260823`  
Decision: **passed; retain as an explicit benchmark-only candidate**

## Change boundary

The candidate bypasses Redis TCP preflight only when both the dedicated benchmark guard and
`BENCHMARK_REDIS_TCP_PREFLIGHT=disabled` are present. Actual Redis command/connection failures
remain circuit-breaker signals. Normal production and benchmark defaults keep preflight enabled.
Redis retry, fallback, pool, cache, authentication, extraction, retrieval, and business semantics
were unchanged. The generation-based cache invalidation candidate remained enabled for the
controlled comparison. Holdout was inaccessible and provider cost was zero.

## Gates and controlled recovery

- Pre-load FAST: 8/8 passed.
- Pre-load INTEGRATION: 5/5 passed after correcting the host `DATABASE_URL` to the isolated
  Compose credential. Earlier runs with a wrong password were harness errors, not product results.
- Redis outage: 8/8 requests returned HTTP 200 through fallback; zero TCP-preflight events and
  zero Redis-related HTTP 500s.
- Recovery: 5/5 requests returned HTTP 200 at 38-53 ms after the circuit recovery window.
- Post-load FAST: 8/8 passed.
- Post-load INTEGRATION: four suites passed initially. One mocked tenant-deletion Qdrant-count
  case failed once, then its exact node and full fault-injection suite passed on rerun. This is
  recorded as transient fixture drift, not a reproducible product regression.

The two API-level failures were duplicate-event `409 Conflict` responses generated by the frozen
idempotency workload, not Redis failures. All audited invariants passed: single winner, winner

fallbacks are a conservative combined count rather than LOW-only traffic. Even with that inclusion,
the reduction from the 3,229 reference is 97.9%.

## Decision and next boundary

The experiment passes its predefined acceptance criteria and explains the previous LOW tail:
the separate TCP probe was producing false circuit pressure despite healthy Redis command/pool
latencies. Keep the guarded bypass available for benchmark evidence. Do **not** change the normal
production default without a separate production-safety decision, because the TCP probe may still
provide value in deployment environments unlike the disposable stack.

The next step should be a separate approval decision: either promote command-driven Redis health
signalling to production configuration with staged rollback monitoring, or retain preflight in
production and continue to the next benchmark phase. No MODERATE run was started here.
